## 1. הבחנה יסודית: QA לעומת ביקורת אבטחה (Security Auditing)
סטודנטים רבים מתבלבלים בין בדיקות איכות תוכנה (QA) לבין ביקורת אבטחת קוד (Code Auditing):
* **בדיקות QA (Quality Assurance):** בודקות האם המערכת עושה את מה שהיא **אמורה** לעשות בשימוש תקין (Functional Requirements).
  * *משל מעולם הרכב:* בדיקת QA מוודאת שהרכב נוסע קדימה, נעצר כשלוחצים על הברקס ומדליק אורות איתות.
* **ביקורת אבטחה (Security Auditing):** בודקת האם המערכת מבצעת פעולות שהיא **לא אמורה** לבצע כאשר מוזן קלט זדוני, בלתי צפוי או קיצוני (Non-Functional Security Constraints).
  * *משל מעולם הרכב:* ביקורת אבטחה בודקת מה יקרה אם תוקף ימשוך בבלם היד תוך כדי נסיעה ב-150 קמ"ש או יזין דלק מהול במים.

## 2. תבנית רשמית לממצא ביקורת קוד (Audit Finding Template)
בבחינות הקורס ובממ"נים, בעת ניתוח קוד זדוני או חולשת אבטחה, נדרשים למלא ממצא ביקורת במבנה מוגדר. להלן התבנית והשדות הנדרשים לבחינה:

| שם השדה בממצא | תיאור והסבר למבחן | דוגמה מעשית משאלת מבחן |
| :--- | :--- | :--- |
| **מיקום בקוד (Location)** | הקובץ, הפונקציה או מספרי השורות הרלוונטיות. | `user.cpp` בפונקציה `checkPassword()` שורה 42 |
| **סיווג החולשה (Classification)** | סיווג לפי **מימוש** (Implementation), **עיצוב** (Design), או **תפעול** (Operational). | חולשת מימוש: גלישת חוצץ במחסנית (Buffer Overflow) |
| **פגיעה במודל CIA** | הגדרת רכיב האבטחה שנפגע: **Confidentiality** (סודיות), **Integrity** (שלמות), או **Availability** (זמינות). | פגיעה בסודיות ובשלמות (דריסת זיכרון והרצת קוד זדוני) |
| **השפעה ועוצמת הנזק (Impact)** | מה התוקף מרוויח כתוצאה מניצול החולשה? | מעקף מנגנון ההתחברות והשגת הרשאות מנהל מערכת (Admin) |
| **אפחות ותיקון (Mitigation / Remediation)** | הפעולה ההנדסית הנדרשת לתיקון החולשה. | החלפת `strcpy` הבלתי מוגנת ב-`strncpy` או מעבר ל-`std::string` |

## 3. זיקה בין פגיעה ב-CIA לבין סוג האפחות (Mitigation)

| היעד שנפגע (CIA) | משמעות האיום | מנגנוני אפחות מומלצים למבחן |
| :--- | :--- | :--- |
| **Confidentiality (סודיות)** | חשיפת מידע רגיש לגורם בלתי מורשה. | הצפנה (AES/TLS), שאילתות פרמטריות, הלבנת קלט (Input Sanitization), והרשאות מינימליות. |
| **Integrity (שלמות)** | שינוי, דריסה או סילוף נתונים ללא הרשאה. | אימות חתימה דיגיטלית, בדיקות גבולות זיכרון (Bounds Checking), ו-Check_Access. |
| **Availability (זמינות)** | השבתת השירות או מניעת גישה ממשתמשים לגיטימיים. | הגבלת קצב (Rate Limiting), Timeout לסוקטים, ניהול זיכרון זהיר (מניעת Memory Leaks / DoS). |

## 4. ניהול סיכונים, מדדים ומידול איומים (Risk, Metrics & Threat Modeling)

### נוסחת הסיכון (Risk Equation):
$$	ext{Risk} = 	ext{Likelihood (סבירות)} 	imes 	ext{Impact (נזק)}$$

### מדדי חולשות וסיווגים לבחינה:
* **CWE (Common Weakness Enumeration):** סיווג סוג החולשה ברמת התכנון/הקוד (למשל CWE-121 עבור Stack-based Buffer Overflow).
* **CVE (Common Vulnerabilities and Exposures):** מזהה ייחודי לחולשה ספציפית שהתגלתה במערכת/מוצר (למשל CVE-2021-44228).
* **CVSS (Common Vulnerability Scoring System):** ציון מורכב בין 0.0 ל-10.0 המדרג את חומרת החולשה (משלב Base Score, Temporal Score, Environmental Score).

### מודל STRIDE לזיהוי איומים:
1. **Spoofing (זיוף זהות):** פגיעה באימות (Authentication).
2. **Tampering (סילוף נתונים):** פגיעה בשלמות (Integrity).
3. **Repudiation (התכחשות):** פגיעה ביכולת התיעוד והאי-התכחשות (Non-Repudiation / Logging).
4. **Information Disclosure (דליפת מידע):** פגיעה בסודיות (Confidentiality).
5. **Denial of Service (מניעת שירות):** פגיעה בזמינות (Availability).
6. **Elevation of Privilege (הרמת הרשאות):** פגיעה בהרשאות ובבקרת גישה (Authorization).

## 5. עקרונות יסוד בתכנון דפנסיבי (Defensive Architecture Principles)
* **Defense in Depth (הגנה לעומק):** שילוב מספר שכבות הגנה בלתי תלויות. אם שכבה אחת נכשלת ( למשל ASLR), השכבה הבאה (כגון Stack Canary או DEP) תבלום את התקפה.
* **Principle of Least Privilege (הרשאות מינימליות):** הרצת כל רכיב במערכת עם ההרשאות המינימליות הנדרשות בלבד לביצוע תפקידו.
* **Fail-Safe Defaults (ברירת מחדל בטוחה):** במקרה של שגיאה או תטקלה, הגישה תיחסם כברירת מחדל (`deny by default`).
* **Complete Mediation:** בדיקת הרשאות ואימות קלט בכל קריאה וקריאה, ללא הסתמכות על תוצאות בדיקות קודמות שנשמרו בזיכרון מטמון לא מאובטח.
