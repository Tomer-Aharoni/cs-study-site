## 1. הבחנה יסודית: QA לעומת ביקורת אבטחה (Security Auditing)
סטודנטים רבים מתבלבלים בין בדיקות איכות תוכנה (QA) לבין ביקורת אבטחת קוד (Code Auditing):
* **בדיקות QA:** בודקות האם המערכת עושה את מה שהיא **אמורה** לעשות בשימוש תקין (Functional Requirements).
  * *משל:* בדיקת רכב שבה מודדים אם הבלמים עובדים כשלוחצים על הדוושה.
* **ביקורת אבטחה:** בודקת האם המערכת מבצעת דברים שהיא **לא אמורה** לעשות כאשר מוזן קלט זדוני, בלתי צפוי או קיצוני (Non-Functional Security Constraints).
  * *משל:* בדיקת אבטחה שבה בודקים מה יקרה אם ימשכו בבלם היד תוך כדי נסיעה ב-150 קמ"ש.

### 🎯 מלכודת מבחן: הבדל בין באג רגיל לחולשת אבטחה (Vulnerability)
* **באג רגיל:** שגיאה בקוד שגורמת להתנהגות בלתי צפויה או לקריסת התוכנית בשימוש תקין.
* **חולשת אבטחה (Vulnerability):** טעות בכתיבת קוד או בתכנון המאפשרת לתוקף לבצע **פעולות בלתי מורשות** (כמו הרצת קוד, מעקף אימות או גניבת מידע).

## 2. עקרונות תכנון תוכנה: צמידות חלשה (Weak Coupling) מול לכידות חזקה (High Cohesion)

שאלת נפוצה מאוד בבחינות (למשל 2021א, 2024):

* **לכידות (Cohesion):** מודדת **עד כמה הרכיבים והשיטות בתוך אותה מחלקה קשורים ומשרתים מטרה אחת יחידה**.
  * *שאיפה דפנסיבית:* **לכידות חזקה (High Cohesion)**. מחלקה צריכה לעשות דבר אחד ולהתמקד בו (Single Responsibility Principle - SRP).
* **צמידות (Coupling):** מודדת **את מידת התלות בין מחלקות שונות במערכת**.
  * *שאיפה דפנסיבית:* **צמידות חלשה (Weak Coupling)**. מחלקות צריכות לתקשר זו עם זו אך ורק דרך ממשקים (Interfaces) ומתודות מוגדרות, מבלי לחשוף או להסתמך על פרטי המימוש הפנימיים.

## 3. תבנית רשמית לממצא ביקורת קוד (Audit Finding Template)
בבחינות הקורס ובממ"נים, בעת ניתוח קוד זדוני או חולשה, נדרשים למלא ממצא ביקורת במבנה מוגדר. להלן התבנית והשדות הנדרשים:

| שם השדה בממצא | תיאור והסבר | דוגמה מעשית מהבחינה |
| :--- | :--- | :--- |
| **מיקום בקוד (Location)** | הקובץ, הפונקציה או מספרי השורות הרלוונטיות. | `user.cpp` בפונקציה `checkPassword()` |
| **סיווג החולשה (Classification)** | סיווג לפי **מימוש** (Implementation), **עיצוב** (Design), או **תפעול** (Operational). | חולשת מימוש: גלישת חוצץ במחסנית (Buffer Overflow) |
| **פגיעה במודל CIA** | הגדרת רכיב האבטחה שנפגע: **Confidentiality** (סודיות), **Integrity** (שלמות), או **Availability** (זמינות). | פגיעה בסודיות ובשלמות (דריסת זיכרון והרצת קוד זדוני) |
| **השפעה ועוצמת הנזק (Impact)** | מה התוקף מרוויח כתוצאה מניצול החולשה? | מעקף מנגנון ההתחברות והשגת הרשאות מנהל מערכת (Admin) |
| **אפחות ותיקון (Mitigation / Remediation)** | הפעולה ההנדסית הנדרשת לתיקון החולשה. | החלפת `strcpy` הבלתי מוגנת ב-`strncpy` או מעבר ל-`std::string` |

## 4. זיקה בין פגיעה ב-CIA לבין סוג האפחות (Mitigation)

| היעד שנפגע (CIA) | משמעות האיום | מנגנוני אפחות מומלצים למבחן |
| :--- | :--- | :--- |
| **Confidentiality (סודיות)** | חשיפת מידע רגיש לגורם בלתי מורשה. | הצפנה (AES/TLS), שאילתות פרמטריות, הלבנת קלט, והרשאות מינימליות. |
| **Integrity (שלמות)** | שינוי, דריסה או סילוף נתונים ללא הרשאה. | אימות חתימה דיגיטלית, בדיקות גבולות זיכרון (Bounds Checking), ו-Check_Access. |
| **Availability (זמינות)** | השבתת השירות או מניעת גישה ממשתמשים לגיטימיים. | הגבלת קצב (Rate Limiting), Timeout לסוקטים, ניהול זיכרון זהיר (מניעת Memory Leaks / DoS). |

## 5. מלכודת מבחן טיפוסית: "אפחות" (Mitigation)

* **שאלה אמריקאית שכיחה (2021א מועד 74):** "מה פירוש המושג אפחות (Mitigation)?"
  * **תשובה נכונה:** הגנת המערכת בפני תקיפה לצורך מזעור הנזק העלול להיגרם ממנה.
